# SDK Full-Flow Test Plan

## Purpose

This document tracks the executable AstrBot SDK test path for Humanize. It is
not a generic benchmark: its evidence answers whether the plugin preserves its
required safety and continuity behavior across an SDK event, an LLM response,
outbound dispatch, and the shared SQLite audit trail.

The production plugin still uses AstrBot 4.26's in-process hook API. The SDK
worker bridge is not present in that Core version, so an SDK-native test adapter
must call the real Humanize service modules without claiming to execute
`main.py`'s production hook chain.

## Full-Flow Contract

The temporary SDK-native adapter will instantiate real Humanize components:

- `SQLiteRepository` against a pytest-owned `humanize.db`;
- `EnvelopeBuilder`, `JargonMatcher`, `ContextComposer`, `ProtocolParser`, and
  `HumanizeService` from this checkout;
- an SDK `Context.llm.chat(...)` call satisfied by `PluginHarness`'s mock LLM;
- `event.reply(...)` only after `process_final_response(...)` returns a valid
  `Reply` outcome.

It will translate trusted SDK event metadata into `MessageContext`. The adapter
will expose captured prepared sections and repository rows to the test only;
that diagnostic path is not production plugin behavior.

## Acceptance Matrix

- [x] A valid `Reply` reaches `RecordedSend` with every parsed message in order.
- [x] A valid `No Reply` produces no outbound message and a successful audit.
- [x] An invalid model response produces no outbound message, no jargon learning,
  and an `invalid_control_header` audit record.
- [x] `prepare_request` supplies ordered current-message, known-terms, and
  response-protocol sections before the SDK mock LLM receives its request.
- [x] A valid `UnknownTerms` item is persisted, then injected on a later matching
  request in the same scope only.
- [x] The same term is absent in a different scope.
- [x] Context trace and protocol audit are stored in the same temporary SQLite
  database, with the expected request and scope identifiers.
- [x] The test avoids memory/OpenViking network operations and does not claim
  memory recall coverage. That has its own integration phase.

## Commands

SDK-only regression and the narrow protocol probe are already reproducible:

```bash
cd D:/Code/Python/_root/SDKs/astrbot-sdk
uv sync --extra dev
uv run pytest -q

cd D:/Code/Python/_root/AstrBot/data/plugins/astrbot_plugin_humanize
ASTRBOT_SDK_PATH=D:/Code/Python/_root/SDKs/astrbot-sdk \
  D:/Code/Python/_root/SDKs/astrbot-sdk/.venv/Scripts/python.exe \
  -m pytest -q tests/test_sdk_runtime_probe.py
```

Create or refresh the combined environment from the persistent SDK workspace:

```bash
cd D:/Code/Python/_root/SDKs/astrbot-sdk
uv venv .venv-humanize --python 3.12
uv pip install --python .venv-humanize/Scripts/python.exe --editable ".[dev]"
uv pip install --python .venv-humanize/Scripts/python.exe --editable D:/Code/Python/_root/AstrBot
```

Run both SDK layers from the plugin directory:

```bash
ASTRBOT_SDK_PATH=D:/Code/Python/_root/SDKs/astrbot-sdk \
  D:/Code/Python/_root/SDKs/astrbot-sdk/.venv-humanize/Scripts/python.exe \
  -m pytest -q tests/test_sdk_runtime_probe.py tests/test_sdk_full_flow.py
```

Do not substitute AstrBot's running environment or production data directory
for `.venv-humanize` or the pytest-owned database.

## Boundaries and Risks

- Passing these tests proves SDK-facing behavior of the test adapter and the
  invoked Humanize services. It does not replace Core-hook integration tests.
- `ContextComposer` imports AstrBot Core token-counter types, so the SDK-only
  environment cannot run the full flow by itself.
- User-facing "good effect" remains a product question. Deterministic tests
  establish non-negotiable safety and continuity contracts; a benchmark needs a
  separately agreed scenario rubric, labels, and scoring method.
